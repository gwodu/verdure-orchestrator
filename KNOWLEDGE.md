# Verdure — KNOWLEDGE.md

Verdure is the **cheapest, safest, and easiest way to use AI in daily life** — the user's **local AI conductor**: **one simple interface that runs the right local model** for whatever the user wants to do, on their own device, owned by them. Cheapest (free, local), safest (on-device, no data leaves), easiest (one interface — no new apps or workflows to learn). It starts from "what are you trying to do?", picks the right local model, and runs it behind a single Verdure UI. **Agency, not extraction:** Verdure conducts existing OSS models/engines, never builds its own; mission over moat; no data harvesting.

> **👉 Here to build? Start at `knowledge/21-handoff.md`** — current state, alignment, and prioritized next steps (the pickup point for a new session). Then `18` (the pivot: one interface over local models) and `20` (Verdure as personal AI).

> **Note:** As of 2026-06-18 Verdure pivoted from a *launcher that installs separate apps* (the "porter", `15`/`17`) to **one interface that drives headless model engines directly** (`18`). Files `01/14/15/16/17` predate the pivot and are being reconciled — read them through the lens of `18`.

This file is an orientation index, not a content store. Knowledge lives in the `knowledge/` subfolder as numbered, modular files. Claude should read this file at the start of every session, then load only the knowledge files relevant to the current task.

This knowledge base is shared across the monorepo: it informs the Phase 0 website (`website/`, the decider/funnel), the **MVP desktop porter** (`app/`, the near-term build — see `17`), and the long-term Rust core (`src/`). The recommendation engine is this knowledge operationalized in code — now a shared workspace package, **`@verdure/decider`** (`packages/decider/`), imported by both the website and the porter so the decision can never differ between surfaces. - 2026-08-21 — **`[OQ-71]` SOLVED: chat ran on Metal, which is wrong on Intel Macs.** Verdure had been doing LLM inference on the **Metal GPU backend** on the founder's 2019 Intel Mac since chat shipped; Metal's kernels target Apple Silicon and on an Intel integrated GPU they return **arithmetically wrong results rather than failing**, which is why weeks of environmental theories (memory, disk, corrupt downloads, quantization, model size, chat memory, the prompt, the sampler) all came back clean. Three things hid it: `Cargo.toml` *claimed* `default-features = false` meant "plain CPU" (it never did — `llama-cpp-sys-2` disables `GGML_METAL` for **watchOS only**); `LlamaModelParams::default()` offloads **every** layer (`n_gpu_layers = -1`); and **every on-device confirmation had come from the two platforms where the bug cannot occur** (iPad = Apple Silicon Metal, correct; Android = no Metal). Fix: choose the backend explicitly in `llm.rs::model_params()` — pin to the CPU **device** via `with_devices` on x86_64 macOS. **`with_n_gpu_layers(0)` alone is insufficient** (Metal still schedules; output stays wrong, just differently) — the device list decides. Proven by toggling: fix off → Metal + `antity@@@@@` return. **Found by building natively for the first time and reading the build log** — the Metal kernel compilation had been printed on every build for months. **Also this session:** Xcode CLT 16.4 + `cmake` installed, so `cargo test` now runs locally in seconds (CLAUDE.md + `testing.md` updated — "CI is the compiler" is retired); `Cargo.lock` committed (which incidentally disproved the "stale `llama-cpp-2` pin" theory — `"0.1.150"` is a minimum, and builds were already resolving 0.1.154); a second CI leak fixed (`paths-filter` diffed the branch against `main`, so every push ran everything); `skills/debugging.md` rewritten on the canonical literature (Agans/Zeller/McConnell) with `[OQ-74]`/`[OQ-75]` recording the evals harness and diagnostic-bundle infrastructure we do *not* have; picker copy fixed so a memory warning reads as an action, not a refusal; and iOS build #13 finally shipped (Markdown + shorter prompt).

- 2026-08-12 — **Chat memory shipped** (`22-chat-memory.md`, resolves the core of `[OQ-59]`). The chat had **no memory at all** — `decide()` built a prompt of `SYSTEM + one message`, so the 1024-token window sat nearly empty every turn; the fix was never about growing the context. Three parts of one mechanism: (1) **send the transcript** in the model's own template; (2) **keep the weights resident** across messages (re-reading 0.4–1.4 GB per message was the dominant cost and what made history unaffordable — `LlamaBackend` also became a process-global `OnceLock` instead of being re-initialised per message); (3) **evict whole turns** when the window fills, never token-level — llama.cpp's context shift would cut mid-turn and leave a dangling marker. The window is now sized **per device and per model** from KV-cache arithmetic (`2 × layers × kv_heads × head_dim × 2B`): ~12 KB/token on the 0.5B vs ~144 KB on the 4B, so one fixed `n_ctx` was simultaneously too stingy and too risky; capped at 4096 by *prefill time*, not just memory. One formula serves all three platforms because it reads `available_ram_mb`, which macOS/iOS/Android already compute their own honest way. **No context-length setting** — deliberate (`design.md`: the jargon knob Verdure exists to delete). Deferred with reasons: summarizing evicted turns `[OQ-68]`, releasing the resident model on background `[OQ-69]`, calibrating the constants `[OQ-70]`, KV-cache reuse across turns (needs a self-referential struct — measure first). Cross-session persistence is a separate change.
