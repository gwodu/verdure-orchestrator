This is the living index of every unresolved question across the Verdure knowledge base. Each entry has a stable `[OQ-XX]` reference code that is cross-linked from the file where the question first appeared.

When a question is resolved:

- [ ] **[OQ-74]** A deterministic harness around the non-deterministic model (`skills/debugging.md`). Verdure has no golden-output eval suite, no tokenizer-parity check, and no quantization regression check — so "the model is bad" and "our code is broken" can only be separated by hand, which is exactly what made `[OQ-71]` take three sessions. **What to build, in order of value:** (a) **tokenizer parity** — assert our prompt tokenizes to the intended control tokens (llama.cpp ships `tests/test-tokenizer-0`; our reference build has `llama-tokenize`); (b) **golden outputs** — ~100 cases pinned at `temperature=0`, fixed seed, **single sequence and fixed batch size**, including one regression case per past bug; (c) **quantization regression** — `llama-perplexity --kl-divergence-base` against an f16 baseline for each quant we ship. **Threshold that changes the plan:** if golden outputs vary run-to-run at temp=0 single-slot, we have a *numerical* determinism problem (batch invariance — live for us since `llm.rs` chunks prefill by `n_batch`) and that must be fixed before the harness is trustworthy. Note temp=0 gives *sampler* determinism, not *system* determinism. (From `skills/debugging.md`; research 2026-08-21.)

- [ ] **[OQ-58]** Model-runtime robustness: ggml calls `abort()` (SIGABRT) on a failed allocation, crashing the whole app (caused the 8 GB chat OOM crash). Isolate inference in a separate process so a model failure surfaces as an error, never takes down the UI. P0 before real users. (From `21-handoff.md`.)

  **2026-08-22 — written out for a go/no-go on distribution.**

  **The mechanism.** llama.cpp and whisper.cpp are compiled *into* our binary. They come from a command-line lineage where the correct response to an impossible state is "print and exit" — so on a failed allocation ggml calls `abort()`, raising `SIGABRT`. That is not an exception and **cannot be caught from inside the process**: not by `Result`, not by `catch_unwind`, not by any code we are able to write. The OS terminates us. There is no in-process fix; that is the whole reason the answer has to be architectural.

  **What the user sees.** Verdure disappears. Mid-sentence, no dialog, no error, no crash report they'd know what to do with. Their conversation goes with it. For a local-first app whose pitch is trustworthiness, "it vanishes sometimes" is the worst possible failure texture.

  **Where it can fire.** Two places, and the second is the one that gets overlooked:
  1. **Model load.** Gated today — `chat_model_for_available` refuses to load unless free RAM ≥ `runtime_mb`. This is why the numbers are deliberately pessimistic (the 4B gated at 2300 MB while measuring ~1400, `[OQ-64]`). The gate is the mitigation, and the over-caution is the premium we pay for it.
  2. **Every single message.** `llm.rs::decide` builds a **fresh context per turn** (`new_context`, line ~345), allocating a KV cache sized to `n_ctx` — ~147 MB for the 4B at 1024 tokens. That allocation is **not re-gated**, so memory the user consumed elsewhere *after* the model loaded (opened Chrome, started a build) can make turn N fail even though the load succeeded. Resolving `[OQ-59]`'s residual — holding one context instead of rebuilding — would shrink this window but not close it.

  **Actual risk profile, so this is not over-weighted.** Our largest model is 1.4 GB and most Apple Silicon Macs ship 16 GB. On a typical target machine the gate passes with room to spare and the real usage sits far below it — crashes should be rare. The exposure is concentrated on **8 GB machines under memory pressure**, which is exactly the founder's Intel Mac and exactly *not* the median new user. This is a tail risk with a catastrophic presentation, not a constant one.

  **The fix.** Run inference in a **child process** that the UI spawns and talks to over IPC (prompt in, tokens streamed back). When the child aborts, the OS kills only the child; Verdure sees the exit status and says "that model ran out of memory — try a smaller one." UI intact, conversation intact. This is the ordinary architecture for embedding untrusted or crash-prone native code (Chrome tabs, VS Code extension host).

  **What it costs:** a real restructure — a second binary, an IPC protocol with token streaming, child lifecycle/health/restart, and moving model state out of Tauri's in-process state. Runtime overhead is small (IPC serialisation per token). **What it also buys:** permission to stop being pessimistic about `runtime_mb` (users get better models), guaranteed memory reclamation on model switch, and it re-opens grammar-constrained tool calling — removed in 2026-07 precisely because it crashed this way — which is the gate on `[OQ-55]` and the "apps for AI" step of `20`.

  **The decision.** (a) Build it before any public download link. (b) Ship now behind the conservative gate and accept a rare vanish. (c) Ship to a small group told it is early, and build it next. **Recommendation: (c) for a handful of testers, (a) before a public link** — the gate makes it genuinely uncommon on 16 GB machines, the new build stamp makes any report actionable, but a stranger who watches the app vanish once does not file a bug, they delete it.

  **Measured:** binary **15 MB → 30 MB** (x86_64 slice 15,990,832 B + arm64 slice 15,144,848 B), `.app` **16 MB → 30 MB**, `.dmg` **11 MB**. Against a 469 MB–1.4 GB model download, the extra ~15 MB is a few percent of what Verdure actually occupies.

For ARM users this is a large *speed-up* versus the Intel-only build, which ran under Rosetta with NEON disabled and (via `[OQ-71]`'s x86_64 branch) Metal off.
  **Verified:** `file` reports `Mach-O universal binary with 2 architectures`, `vtool` confirms sane per-slice deployment targets (x86_64 `minos 10.15`, arm64 auto-clamped to `11.0` — the forced 10.15 in `.cargo/config.toml` is invalid for ARM and the toolchain corrected it), and the bundle **launches** on this Intel Mac from its x86_64 slice.
  **Cost:** the CI build roughly doubles (~66 → ~130 billable min) because llama.cpp and whisper.cpp compile twice. Acceptable for a build cut once per release rather than per push. *Not yet exercised in CI* — the next `app-build-N` is its first run.
  **Note:** the local `.dmg` step, which fails for the single-arch build (`bundle_dmg.sh` needs Finder automation), **succeeded** for the universal build. Not investigated; don't rely on it.

  **The problem it fixed:** the macOS app could not be distributed to anyone but the founder, because it was Intel-only. `build-app.yml` builds `--target x86_64-apple-darwin` and nothing else (verified 2026-08-22: the shipped binary is `Mach-O 64-bit executable x86_64`). That was the right call while the only test machine was a 2019 Intel Mac, but **every Mac sold since Nov 2020 is Apple Silicon**, so it is the wrong default for anyone else. Such a build does run on an M-series Mac under Rosetta 2 — and for Verdure specifically that is close to a worst case: llama.cpp's ARM NEON kernels never execute, x86 SIMD is translated instruction-by-instruction, and the binary takes the `x86_64` branch of `llm.rs::model_params()` — the one `[OQ-71]` added to **force CPU and disable Metal**. So a brand-new Mac would run Verdure translated, CPU-only, and measurably slower than the old Intel machine it was built for. That directly contradicts the honest-performance principle (`06`/`18`) at the exact moment a new user forms their first impression. **Options:** (a) `--target universal-apple-darwin` — one download, both architectures, but compiles llama.cpp/whisper.cpp twice so a distribution build costs roughly double the macOS minutes; (b) ship two downloads and make the user choose (cheaper, worse UX, and users pick wrong); (c) Apple-Silicon-only and keep Intel local for the founder. **Leaning (a)** — one build per release, not per push, and "it just works" is the whole product thesis. **Must be settled before any public download link exists**, since the first thing a visitor does is run it on an M-series Mac. (From `build-app.yml`; raised 2026-08-22 answering "how do we distribute this?")
- [x] **[OQ-71]** Garbage chat output on Intel macOS — **RESOLVED 2026-08-21. Cause: chat ran on the Metal GPU backend, which returns arithmetically wrong results on a 2019 Intel Mac's integrated GPU** (it does not fail — it computes incorrectly, which is why this presented as a bad model for weeks). Symptom fingerprints: `uids@@@@@`, `antity@@@@@`, multilingual token salad.
  - **Why it hid.** (1) `Cargo.toml` asserted `default-features = false` "keeps it plain CPU (no Metal/CUDA)" — **false**: `llama-cpp-sys-2`'s build script disables `GGML_METAL` for **watchOS only**; every other Apple target inherits llama.cpp's cmake default of ON. (2) `LlamaModelParams::default()` sets `n_gpu_layers = -1`, i.e. offload every layer to the GPU. (3) **Every on-device confirmation came from platforms where the bug cannot occur** — iPad is Apple Silicon (Metal correct), Android has no Metal. We validated on the two platforms structurally incapable of showing it.
  - **Fix:** choose the backend explicitly in `llm.rs::model_params()` — on `x86_64` macOS, pin the model to the CPU device via `with_devices` **and** `with_n_gpu_layers(0)`; unchanged elsewhere. **`with_n_gpu_layers(0)` alone is NOT sufficient** and stopping there is a trap: it moves weights off the GPU but llama.cpp still registers Metal and schedules onto it (436 MiB Metal buffer, 302 graph splits) and the output stays wrong — just *differently* wrong (salad → repeating English). The device list decides the backend.
  - **Proven (rule 9):** fix on → coherent answer, CPU buffers only; fix off → `MTL0 298.5 MiB` and `antity@@@@@` return.
  - **Found by** building natively for the first time and *reading the build log* — the Metal kernel compilation had been printed on every build for months.
  - **Method that worked** (now in `skills/debugging.md`): upstream's prebuilt reference binary on the same model + machine eliminated eight hypotheses in one command; then a minimal in-crate repro (`llm.rs::repro_oq71_generates_from_a_real_model`, `#[ignore]`d) isolated our code from the app shell.
  - **Follow-ups:** does `whisper-rs` also use Metal here? Transcription is *correct* on this Mac (~3.9× real-time), so it either avoids Metal or tolerates it — worth knowing, but **do not "fix" working code** without evidence. Also delete the obsolete Q8_0/fp16 diagnostic models from the picker (they tested the disproven K-quant theory and would ship to users). (From `llm.rs`; founder reports 2026-08-16/17/21.)
