# 25 — The personal context store: what Verdure has seen, kept on the device

**Status:** 🟡 Provisional (the store — entity-centric, structured-first — is built and tested, 2026-10-21, and reshaped 2026-10-22 to `27`'s four nouns: person, place, event, observation, with participation linking a person to an event; the Android notification listener is built and reads **every app** unless unticked since 2026-10-23, `[OQ-100]`, **Pixel first**, unmeasured on the device)

*Role: the **decision + design** for how Verdure builds context about the user — the store's shape, what feeds it, how a question is answered from it, and the rules that keep it private. This is `20`'s "personal context core" (`[OQ-56]`) made concrete, with messages as its first source. Written 2026-10-21 from the founder's two research reports (the messaging hub; storing personal context across Android, iOS and macOS) and the direction decided with him the same day. Claims from the research that this file relies on were re-verified against their sources where marked ✓.*

## The decision

Verdure does not become a messaging app. It becomes the place that **already knows** — the user asks *"what did Tunde say about the rent?"* or *"whose birthday is coming up?"* in the same chat they use for everything, and Verdure answers from what it has seen, with the source attached and tappable, exactly as it answers from the web (`24`). The "central messaging hub" the founder started from is one *source* of that knowledge and one transparency page, not a second inbox to maintain.

Three facts from the research shape it:

1. **No official API exists for personal WhatsApp, Instagram, Messenger, Snapchat, LinkedIn or Discord.** Every "all your chats in one place" product rests on reverse engineering, and the ban lands on the *user's* account — the one thing a Nigerian user can least afford to lose. The only zero-risk route is Android's notification layer: it sees what the official app chose to show, and replies through the app's own reply action. Telegram (TDLib), X (its new Chat API), Slack and Gmail are the sanctioned exceptions.
2. **Nothing may be relayed through a Verdure server.** Sunbird/Nothing Chats (2023) relayed decrypted messages through a cloud and leaked them; it is the category's one existential failure. On-device also shrinks the NDPA/PIPEDA position to almost nothing: Verdure the company never processes the third parties' data.
3. **This is Android.** iOS gives apps no access to other apps' notifications, SMS, or anything else. The store itself is cross-platform; the feeds are Android-first, with Telegram's official API the only cross-platform feed in sight.

## The store

One SQLite file, `context.sqlite`, in the app's private folder beside the models (`app/src-tauri/src/context.rs`). **Not a "notifications table"**: a notification is a transport, and what it carried is an **observation** — something that happened at a time — the same shape whether it arrived as a WhatsApp notification, an SMS, a chat export the user shared in, a call, or a photo's time and place. **Entity-centric**: people are rows, and every observation points at the person it came from, because the questions that matter most are about people and time, not words. The shape is `27`'s **four nouns and one link** — person, place, event, observation, participation — chosen from the map of everything a phone can give (`27`), so that "mark things by events, and know this person was at this event at this time" is a table, not a feature.

| Table | Holds | Notes |
|---|---|---|
| `sources` | which feeds are on: kind (`notification` / `sms` / `chat_export` / `calendar` / `photos` / `call_log` / `user`) × app | the per-app opt-in list the user sees |
| `person` | who, once | `is_self` marks the user |
| `person_alias` | the normalised names a person goes by ("tunde bakare", "tunde") | how "Tunde" resolves; the user can add nicknames |
| `identity` | (app, the app's key for a sender or contact) → person | how WhatsApp's "Tunde" and the SMS number become one person — **only when the user merges them** |
| `place` | a name (unique in normalised form), optional coordinates and address | reused by events and observations |
| `event` | a title, a span, an optional place, an **origin** (`given` by a calendar, with the app and OS id so it can be re-read; or `inferred`), a dedupe key | a re-read of the calendar updates, never duplicates; an inferred event dedupes on title + start |
| `participation` | **person × event × role** (`organiser` / `invited` / `attended` / `mentioned`) + which source said so | the founder's sentence as a table; indexed by person |
| `threads` | where a message lives: app + a stable key (Android's conversation id, a phone number, an export's chat name) + title + group? + last activity | messages only |
| `observation` | **one table, one time axis, every kind** (`message` / `call` / `photo` / `visit` / `note`): kind, source, app, time, text, optional place and event; for messages also thread, sender, **sender's person**, direction `in`/`out`; **dedupe key (UNIQUE)** | indexed by time, (kind, time), (person, time), (thread, time), event |
| `observation_fts` | FTS5 over text + who (sender / person) + where (thread title / place) | the keyword tier; a photo with no words is still found by where it was taken |
| `facts` | extracted later while charging: kind (`birthday` / `plan` / `amount` / `deadline` / `address`), subject person, value, when, **valid-from / valid-to**, confidence, which model — **each pointing at the observation it came from** | step 4; facts are invalidated, not deleted (Zep's bi-temporal idea, the one part of agent-memory systems that transfers to a phone) |
| embeddings | observation → vector | step 5, only if the keyword tier measurably misses |

**The identity rule on ingest:** the app's key for the sender if seen before; else a person whose alias is exactly this name (so "Tunde" across two WhatsApp threads, or on WhatsApp and Telegram, is one person); else a new person. Two different full names are never merged by guesswork — that is the user's call (`merge_people`), surfaced as a suggestion later. Two "Jacksons" make `find_person` answer *Ambiguous*, which becomes a question back to the user, never a confident answer from the wrong one.

**Contacts are not copied; calendar events get a thin row.** Contacts are queried live from the OS at question time (`ContactsContract`/`Contacts`): local, offline, already indexed, and copying them would add staleness and double the privacy surface. Only the alias/identity link needed to join "events with Tunde" to a person lives in the store. A calendar entry, though, becomes an `event` row (title, span, place, the OS's id) — a participation link needs a stable row to point at — and the OS stays the truth: the row is refreshed from `CalendarContract`/`EventKit` whenever it is read, and `upsert_event` makes a re-read an update, never a duplicate (`27`).

**Dedupe matters more than it looks.** Android re-posts the whole conversation every time a notification updates, and a user can share the same export twice; the key is a stable FNV-1a hash of (app, thread, sender key, time, text), so re-posts and re-imports store nothing. **Tuning matters more than engine choice:** WAL with `synchronous=NORMAL` (the UT Austin SQLite benchmarking study, APSys 2017, measured up to 11.8× on Android from the journal mode alone) and an 8 MB page-cache cap so the store never competes with a model for RAM. Migrations are appended with a version check and never edited: a store on a phone must survive every version of the schema that ever shipped. SQLite + FTS5 (+ sqlite-vec later) covers every retrieval mode in one file, one encryption story and one Rust dependency; the platform-native stores (Room, Core Data, AppSearch, Core Spotlight) are unreachable from Rust and would split the core.

## How a question is answered

**In a fixed order: structured, then keyword, then (maybe, later) vector.** The founder's example questions are lookups, not retrieval: *"the last thing Tunde said"* is `items WHERE sender_person_id = ? ORDER BY at_ms DESC LIMIT 1`; *"what am I doing on the 25th"* is a date range against the calendar provider. Vector similarity has no reliable notion of recency, exact dates or who someone is — exactly what these questions turn on. So:

1. **Rules in Rust turn the question into a typed query.** A name → `find_person` (exact alias, then prefix, then a word of an alias; ambiguity is a question back). A date expression ("Dec 25", "last week", "this morning") → a `[start, end)` range against the device timezone — a rule, never the model's job. An app name → a scope. (The date parser and the router are step 2.)
2. **Then the matching lookup runs:** `last_from(person)`, `in_range(start, end, person?)`, a live calendar query, or — only when the question is about *words* — the keyword tier: content words, stopwords dropped, each a quoted prefix match (`"tunde"* OR "rent"*`, so nothing a user types can break FTS5), BM25 with text weighted over sender over thread title, newest first on ties, optionally scoped to the resolved person.
3. **The records are serialised compactly** (`[WhatsApp, 2026-05-12 — Tunde]` + text, ~20–25 tokens each) through the same `web::sources_block` the web search uses, **at most 8–12 of them**, and answered with `[n]`; the footer's `[n]` opens that conversation. **For a pure lookup — the last message, today's events — render the record to the user directly and let the model only phrase it, or not at all.**
4. **Embeddings only when the keyword tier measurably misses** on real questions (`[OQ-101]`), per device tier: off on 4 GB phones, on charge only on 6–8 GB. The cheap candidate is a static Model2Vec model (`potion-base-8M`: 30 MB, MIT, loadable from a folder by `model2vec-rs` ✓), not a transformer.

**Why so little context, verified ✓:** Pandey et al., *Can Small Language Models Use What They Retrieve?* (arXiv:2603.11513, March 2026, models 360M–8B): even with *oracle* retrieval, models ≤7B fail to extract the answer 85–100 % of the time on questions they can't answer alone, and adding retrieved context overturns 42–100 % of answers they previously got right — "the bottleneck is context utilization, not retrieval quality … a net negative trade-off" below 7B. A separate benchmark (arXiv:2601.07790) reports Qwen3-4B at 95.6 % *with* RAG on its task ✓ while the 1.7B degrades (its exact figure wasn't on the abstract page — unverified). Our own iPad run agreed: the 4B grounded and cited, the 2B used results without citing, the smaller models ignored them. The design conclusion: few, exact records, found by rules; and the model is the last step, not the first. Every answer shows its sources so a wrong one is visibly wrong — the same honesty the web search has.

## What feeds it, in order

1. **Android notification listener** (`[OQ-100]`, **built 2026-10-22, unmeasured**): a small Kotlin `NotificationListenerService` written into the Tauri Android project by `patch-android-project.py` (which already patches `MainActivity` for the microphone). **It never calls native code**: a background service that crashed inside Rust would take the listener down with it, so it appends one JSON line per message to `context.spool` in the app's private folder and the app drains the spool into the store whenever it runs (`context::drain_spool`, rename-then-read so the hand-off is atomic). **Every app is read unless the user unticks it (founder, 2026-10-23)** — the opt-in list became an opt-out list, `context.off`, one package per line, because the point is everything the phone shows: a reminder, a receipt, a delivery, an email's subject line are the user's life as much as a chat is. The service skips the system's own packages, ongoing notifications (a call in progress, a download, a foreground service's own notice) and machinery categories (playback, progress, status, timers, navigation). What is not a conversation lands as an observation of kind **`notice`** — app, time, `title: text`, no thread — found by words and by date like any other record, counted per app on the memory page, and forgettable per app. Read the **structured** conversation, not the text: WhatsApp, Telegram, Messenger and Google Messages post `MessagingStyle` notifications — `EXTRA_MESSAGES` with sender (`getSenderPerson()`, with a key where the app gives one), text, timestamp, group flag, conversation title — which maps straight onto `items` with a real `sender_key`. Skip `FLAG_GROUP_SUMMARY` and "N new messages" collapses; iterate *messages*, not notifications, and let dedupe absorb the replay. Instagram and Snapchat are weaker (plain text; content-free "sent you a snap"). Insert in the callback in one transaction and defer everything else to charging-constrained work. Per-app opt-in. Direct Reply through the app's own `RemoteInput` while the notification is alive; otherwise a deep link into the app. **Never auto-send** (`06` principle 4). **Three hard limits, verified ✓:** (a) Android's reference: *"Notification listeners cannot get notification access or be bound by the system on low-RAM devices running Android Q (and below)"* — Android Go-class phones on Android 10 or older cannot use this feed at all, and the product must say so (`[OQ-102]`); (b) Android 15 redacts notification content where an OTP is detected for untrusted listeners, and the bypass permission is reserved for system roles — accept it as a privacy feature; (c) the service "will likely be killed" after `onListenerDisconnected()`, OEM battery managers unbind it, and `requestRebind` plus a visible "listener connected" health check are the only remedies.
2. **Chat export** (built, 2026-10-21): the one-time, user-driven way to give Verdure a conversation's past. WhatsApp's "Export chat" is **per chat** and about five taps, so this is "bring in the three people that matter", not a migration — the honest line is *Verdure's memory starts the day you turn this on.* `parse_whatsapp_export` handles the Android and iOS forms, 12/24-hour clocks, multi-line messages, system lines, and marks the user's own side `out`. Dates carry no timezone and follow the phone's locale (`[OQ-99]`).
3. **Calendar and contacts, live** (step 2, all three platforms): `CalendarContract`'s `Instances` (recurrence expanded by the OS) and `ContactsContract` on Android; `EventKit` (full access, iOS 17+'s `requestFullAccessToEvents`) and `Contacts` on iOS/macOS. This is what gives **iOS a real role**: "what am I doing on the 25th" and "events with Tunde" work on the iPad even though no message feed ever will.
4. **Telegram via TDLib** (later): the one platform with full history through an official client API — and the only message feed that would also work on iOS.
5. **macOS importers** (later, optional): with Full Disk Access the Mac can read the Notification Center database and Messages' `chat.db` — richer than either phone, through undocumented, version-fragile formats; read-only, copied into the store, version-gated. A possible dev-time source on the founder's Mac, not a product promise.
6. **SMS/call log as the default handler** — Play grants `READ_SMS` only to the default SMS/Phone/Assistant handler; declarations get rejected when they don't match the core feature. Plan v1 without it; SMS *notifications* still arrive through the listener.

**The iOS ceiling, stated honestly:** no third-party app can read other apps' notifications, Messages or Mail, and nothing in Apple's 2024–26 developer material changes that; Apple's own personal context (Siri's semantic index) can be *written to* via App Intents, never read. On iOS the store holds calendar/contacts answers, what the user shares in (a Share Extension: "share this chat to Verdure"), Shortcuts input, and Verdure's own conversations. *"The last thing Tunde said on WhatsApp" is not answerable on an iPhone, and Verdure will say so rather than fake it.*

What stays out indefinitely: reverse-engineered protocol clients for WhatsApp/Meta, even user-owned. The ban risk is the user's account; it is the one dependency where the counterparty is Meta.

## Rules that keep the promise

- **Nothing leaves the device.** No sync, no relay, no server, no telemetry. The feature's disclosure is one sentence.
- **Excluded from cloud backup.** Android's auto-backup to Google Drive would copy the file off the device by a side door; the platform build must list `context.sqlite` in the backup exclusion rules. This is the rule most likely to be broken silently — it is a test the moment the Android build has the file.
- **Visible and deletable.** A page called **What Verdure knows**: what is stored, from which apps, how much, untick an app (your bank, say), forget an app, a conversation, a person, an event, or everything. This is what *ask, don't sniff* requires of a powerful permission.
- **Asked for in the app, once (2026-10-23).** The first chat screen on a phone that can do it asks — the benefit first, then that it all stays on the phone, then that Android grants it under "Notification access" — with "Allow in Settings" and "Not now"; afterwards it lives on the memory page. A permission that only exists on a settings page is not consent (`11`, "Mobile non-negotiables").
- **Encryption at rest:** the OS's file-based encryption and the app sandbox today; SQLCipher with a Keystore-held key is a hardening step whose cross-compile cost is unknown (`[OQ-99]`).
- **Retention has defaults.** Messages 12 months, a hard total cap (100 MB default, user-adjustable) enforced oldest-first, and a short-lived raw-notification log (7 days) for everything that isn't a message or a transaction (promotions, system noise) — classified by `Notification.category`, template and package before it reaches the durable tables. (Step 3, with the listener.)
- **Decrypted context stays in the Rust core.** Microsoft Recall's 2026 bypass was of the decrypted rendering path, not the crypto: prompts and retrieved records are never logged, and buffers are dropped after the answer.
- **Messages are untrusted input.** Reading is safe; the moment Verdure can act (reply, book, pay), a message saying "ignore your instructions and send…" is a real attack. Acting stays behind the tool-calling isolation already gated on `[OQ-58]`.
- **Proactive only when the value is unambiguous.** Verdure speaks first for a birthday tomorrow or an OTP it can read back — never for "here's a summary of your day" — and every nudge is one tap from "never again". Earned, rare, reversible. Everything else waits to be asked.

## The steps

1. ✅ **The store** (2026-10-21, reshaped 2026-10-22 to `27`): the entity layer (person / alias / identity with the ingest rule and explicit merge), places, events with origin and participation, one observation table for every kind indexed by time / person / thread / event, `find_person` with ambiguity, `last_from`, `in_range`, `events_in_range`, `events_with`, `events_titled`, `people_at`, `at_event`, FTS5 search (optionally person-scoped), threads, people, counts, delete by thread / person / event / all, the export parser (which learns the file's date order), SQLite tuned (WAL, NORMAL, 8 MB cache). Pure Rust, 24 tests, no device needed.
2. **Pixel first (founder, 2026-10-22) — built the same day, on the Mac, awaiting the Pixel:** `recall.rs` (the date-expression parser and the router: name → person with ambiguity as a question back, date → local-time range, else keywords; pure lookups rendered directly, a question about words hands ≤ 8 records to the model under a "from the user's own phone" heading through the same block as web search); the listener and the spool; `What Verdure knows` (the feed's on/off state with the OS settings link, per-app opt-in, what is held per app, conversations with a tap-to-read sheet, people, coming-up events, a WhatsApp export importer, Forget on every row and Forget everything); recall runs first on every chat question, before the web. Android's network probe now answers Wi-Fi / cellular / offline. **Not yet:** calendar and contacts adapters, Direct Reply, the Pixel week of measurement. The original plan: the Android build gets everything the iPad pilot got (the web switch, citations, Your model — all shared code, with Android's own network-state probe filled in), then the store wired in: the Kotlin listener (`[OQ-100]`) feeding `ingest`, the router (name → person, date → range, app → scope, else keywords), the store as a grounding source in chat with pure lookups rendered directly, "What Verdure knows" (apps, people, conversations, events, delete), "share an export to Verdure". Then calendar and contacts as the first event and people sources. Measure on the Pixel 8a over a week: capture rate, reply success, battery, survival under OEM battery managers. Android builds are 1× billing. Kill-criteria from the research: under 90 % capture on the target Transsion devices means "digest of what you saw", not "replace the apps".
3. **iOS later**, only what its column in `27` allows: calendar, contacts, exports, Verdure's own conversations.
4. **Facts while charging** on the 4B → the birthday question.
5. **Embeddings**, only if step 2 shows keyword search missing.

## Open Questions

- `[OQ-99]` Export dates: the parser now learns day/month order from any day > 12 in the file; a file with every day ≤ 12 is still read day-first, and exports carry no timezone. Encryption at rest beyond the sandbox (SQLCipher via `rusqlite`'s `bundled-sqlcipher`, key wrapped by the Keystore / Secure Enclave, `AfterFirstUnlockThisDeviceOnly`) needs its iOS/Android cross-compile cost measured before it is promised.
- `[OQ-100]` The Android notification listener spike (now every app, opt-out): `MessagingStyle` coverage per app, capture rate, Direct Reply success, battery, OEM battery-manager survival, and Play's prominent-disclosure requirement for notification access. No `AccessibilityService` — Play bars it for this and Android 17 revokes it.
- `[OQ-101]` Retrieval quality: does the rules-first router plus BM25 find the right records for 30–50 real questions, and where does it miss badly enough (paraphrase) to justify an embedding leg? Candidate: `potion-base-8M` via `model2vec-rs` (30 MB, MIT, static — no transformer at query time), stored as int8 or binary vectors in sqlite-vec (pre-v1; pin it). EmbeddingGemma-300M (~200 MB quantised) only on charge, on 6–8 GB devices.
- `[OQ-102]` The floor that can't have the feed: Android Go-class phones on Android ≤ 10 cannot bind notification listeners (official). Decide how the product says so (the feature simply doesn't appear, with one honest line) and measure what share of the target Tecno/Itel/Infinix fleet that is.
